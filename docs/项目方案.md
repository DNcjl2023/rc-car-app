## 第 4 轮：BLE 通信协议设计（2026-08-13）✅ 已定稿

### 4.1 设计原则
1. **二进制定长帧 + CRC8 校验**：7 字节一帧，解析确定、占带宽小，比文本协议更适合高频控制
2. **控制高频、状态低频**：摇杆帧 25Hz，电量帧 5 秒一次，省电省带宽
3. **安全兜底在固件**：ESP32 侧 300ms 看门狗——即使 App 闪退/断连，车也自动停，不依赖 App 自觉
4. **协议与传输解耦**：App 里协议解析层独立，模拟模式与真机共用同一套代码

### 4.2 BLE GATT 服务（FF 系列厂商自定义段）
| 名称 | UUID | 方向 | 用途 |
|---|---|---|---|
| 服务 | `FFF0` | - | 容器 |
| 控制特征 | `FFF1` | App → ESP32（Write Without Response） | 摇杆/配置/命令帧 |
| 状态特征 | `FFF2` | ESP32 → App（Notify） | 电量/电压/设备信息 |

- 广播名：`RC-CAR-XXXX`（XXXX = ESP32 MAC 后 4 位，方便多车区分）
- 连接间隔：15~45ms，slave latency = 0（保证摇杆跟手）
- 7 字节帧远小于 BLE 最小 20 字节包，无需协商大 MTU

### 4.3 统一帧格式（7 字节定长）
~~~text
偏移  0    1    2     3    4    5    6
      0xAA 0x55 Type  D0   D1   D2   CRC8
~~~
- 帧头：`0xAA 0x55`（双字节防误触发）
- Type：帧类型（见下表）
- D0~D2：数据
- CRC8：对偏移 0~5 共 6 字节计算，多项式 0x07、初值 0x00（CRC-8/SMBUS 风格）

#### 帧类型一览
| Type | 名称 | D0 | D1 | D2 |
|---|---|---|---|---|
| 0x01 | 摇杆控制 | 转向 0~254（127=中位） | 油门 0~254（127=停） | 标志位 |
| 0x02 | 参数配置 | 参数 ID | 参数值 0~254 | 0 |
| 0x03 | 命令 | 命令 ID | 0 | 0 |
| 0x11 | 状态上报（ESP32→App） | 电量% 0~100 | 电压高 8 位 | 电压低 8 位 |

#### Type 0x01 摇杆控制帧
- D0 转向：0=最左，127=直行，254=最右（左右镜像由 App 设置页控制）
- D1 油门：0=最大后退，127=停止，254=最大前进（上推前进）
- D2 标志位：
  - bit0（0x01）指令源：0=手动摇杆，1=自动/TikTok（预留）
  - bit1（0x02）急停 STOP：1=立即刹车，保持到收到 bit1=0 的新帧
  - bit2~7 保留（0）

#### Type 0x02 参数配置帧
| 参数 ID | 含义 | 值域 |
|---|---|---|
| 1 | 限速百分比 | 0~100（默认 60） |
| 2 | 转向灵敏度（曲线强度） | 0~254（默认 128） |
| 3 | 摇杆死区 | 0~254（默认 12，约 ±5%） |
| 4 | 舵机中位微调 | 0~254（127=不偏，±127） |

> 限速在固件侧做强约束：即使 App 被第三方改写/误发，速度也超不过设定上限。App 每次连接后把当前设置重发一遍，保证一致。

#### Type 0x03 命令帧
| 命令 ID | 含义 |
|---|---|
| 1 | STOP 急停（立即刹车，等效 bit1=1） |
| 2 | 恢复（解除急停） |
| 3 | 请求电量（立即回 Type 0x11） |
| 4 | 握手/请求设备信息（固件回设备名+协议版本） |
| 5 | 待机（低功耗，舵机回中） |

#### Type 0x11 状态帧（ESP32 → App）
- D0：电量百分比 0~100（0xFF=未知）
- D1|D2：电池电压，单位 mV（例：3.70V = 0x0E 0x74 → 3700mV）
- 推送时机：连接后立即一次 → 每 5 秒一次 → App 请求时立即回

### 4.4 发送频率与防抖
- **控制频率 25Hz**（40ms 一帧）：摇杆拖动时连续发；静止 500ms 后停止发送（省电）
- **死区**：摇杆中心 ±5%（约 ±6/127）不发送；离开死区发第一帧，回中发一次中位帧
- **变化阈值**：偏移变化 ≥2 才发新帧（省无效包）
- **急停**：按下 STOP 立即发命令帧 1，按住期间每秒重发一次，松开发命令帧 2

### 4.5 断线保护（安全第一）
- **ESP32 看门狗**：>300ms 未收到任何有效帧 → 自动回中位/刹车（油门 127、舵机回中），进入"安全态"
- 收到下一帧有效帧自动退出安全态（无需重连）
- **App 侧**：检测到断开 → 本地 UI 立即提示"已断开 · 自动刹车"；自动重连 3 次/10 秒
- 重连成功后 App 重发限速等参数（Type 0x02）并请求电量

### 4.6 电量映射（固件实现）
- 3.7V 锂电池线性映射：3.30V=0%，4.20V=100%；低于 3.30V 报 0%
- 电量 <20%：App 提示"电量低"；<10%：闪烁警告
- （如改 2S/镍氢电池，固件改一张电压对照表即可，协议不变）

### 4.7 模拟模式（协议先行验证）
- App 内置"虚拟 RC-CAR-XXXX"外设：实现同样的 FFF0/FFF1/FFF2 服务
- 模拟逻辑：解析控制帧 → 更新虚拟速度/方向 → 每 5 秒回状态帧；电量从 87% 开始每 30 秒 -1%
- **解析代码与真机共用**（协议层与 BLE 传输层解耦），保证模拟 = 真机行为一致

### 4.8 TikTok 联动预留（本期不开发，协议已留位）
- App 内做"指令源"抽象：Manual（摇杆）/ TikTok / 定时任务，全部输出同一套 Type 0x01 帧
- 已预留：D2 bit0 指令源标记（0=手动 1=自动）
- 后续流程：TikTok 打赏/评论 → App 收到（WebSocket/HTTP）→ 翻译为动作队列（前进 1s、左转 30%、连发加速）→ 按 25Hz 转控制帧
- **ESP32 固件无需改动**：协议不变，联动全部在 App 层实现

### 4.9 关键推荐值（默认采用，可随时调整）
| 项目 | 推荐值 | 说明 |
|---|---|---|
| 帧格式 | 二进制 7 字节 + CRC8 | 比文本省带宽、解析稳 |

### 6.1 硬件变更
| 项 | 原方案 | 新方案 |

| 驱动芯片 | 原车一体板（信号点焊） | **L298N 电机驱动板** |
| 主控 | ESP32 DevKitC | **ESP32-CAM**（内置 OV2640 摄像头 + WiFi/BLE） |
| 连接 | BLE 唯一 | **WiFi 主 + BLE 备** |
| 摄像头图传 | 不做 | **必须做**（MJPEG over WiFi，未来做抖音直播视频来源） |
| 转向方案 | 舵机直驱（3 线） | 待确认：双电机差速 / 保留舵机 |

### 6.2 ESP32-CAM 引脚接线（重要约束）
- ESP32-CAM 可用 IO 很少：GPIO 6~11 被 flash 占用，16/17 被 PSRAM 占用，1/3 是串口
- 按用户指定，L298N 控制接 **12/13/14/15**：
  - GPIO 12 → L298N IN1（左电机）
  - GPIO 13 → L298N IN2（左电机）
  - GPIO 14 → L298N IN3（右电机）
  - GPIO 15 → L298N IN4（右电机）
  - L298N 的 ENA/ENB 接 5V 常开；调速由 IN 引脚输出 PWM（LEDC 通道），实现正反转 + 无级调速
- ⚠️ 技术风险（固件阶段处理）：
  - GPIO 12 = MTDI：上电瞬间若为高电平可能影响 flash 启动 → 需在 L298N 输入端加 10K 下拉电阻，或固件上电初期立即拉低
  - GPIO 0 = BOOT 按钮：本方案不占用
- 转向方案：若为双电机差速车（履带/坦克型），12-15 正好两路电机；若为舵机转向车，需再找可用 IO（候选 2/4/5，需牺牲部分功能）→ **待用户确认车型**

### 6.3 通信架构（WiFi 主 + BLE 备）
- **主链路 WiFi（TCP）**：控制指令 + 摄像头图传
  - 模式 A（推荐，户外/无路由器）：ESP32-CAM 开 AP 热点 `RC-CAR-XXXX`，手机连热点，App 连固定 IP（如 192.168.4.1）
  - 模式 B（家里）：ESP32-CAM 连家里路由器（STA），手机连同一 WiFi，局域网内连接
  - 控制：TCP Socket **端口 3333**，复用第 4 轮 7 字节帧协议（AA 55 Type D0 D1 D2 CRC8）
  - 设备发现：mDNS 广播 `rc-car-xxxx.local` + App 手动输入 IP（兜底）
- **备用链路 BLE**：WiFi 不可用时用 BLE 控制，复用第 4 轮 FFF0 服务与帧协议；BLE 带宽不足，**不含图传**
- **图传**：HTTP MJPEG 流 `http://<IP>:81/stream`（ESP32-CAM 标准做法），控制与视频分离互不影响
- **心跳/断线**：TCP 每 500ms 心跳，>1.5s 无响应判断线；ESP32 侧 300ms 无指令自动刹车（沿用第 4 轮）

## 第 10 轮：供电问题定位与方案（2026-08-25）✅
- **现象**：芯片在底座（USB 5V）秒连 WiFi；装车后（4×南孚 6V → L298N 5V → ESP32）LED 亮但连不上 WiFi（路由器后台历史记录误导过一次，实际车未上线）
- **根因**：4×AA 南孚 6V 太低，L298N 的 5V 稳压（需 ≥7V）输出不足 → ESP32 能亮灯但 WiFi 射频供电不稳
- **GPIO12 上电干扰**：L298N 输入上电可能拉高 GPIO12（MTDI），影响启动——最终接回电机线时需 GPIO12 加下拉电阻（先 10K，不行换 1K）到 GND
- **供电方案（用户确认）**：
  1. 临时：杜邦线串联 18650×2（7.4V）→ L298N 电机电源 → L298N 5V 输出 → ESP32 5V（共地）；注意正负极、防短路、用胶布包好
  2. 后期：买 18650 充放电模块（2S，带 Type-C 充电 + 保护板），充电方便且更安全
- **明日验证顺序**：① 充电宝单独给 ESP32 5V 确认供电是根因 → ② 18650 串联 7.4V 装车 → ③ 确认车上线（IP 192.168.0.108 附近）→ ④ 模拟器 App 连车控制


## 第 11 轮：联调问题与修复记录（2026-08-25/26）
1. **双重限速 Bug（App 前进不动）**：App 和固件都乘了限速 60%，满油门 App 只发 T=203，固件再乘 0.6 → 36% PWM，电机转不动。修复：App 端去掉限速，只在固件端限速（符合协议 4.3 固件强约束）。
2. **L298N 方向控制错误（只能一个方向走/转向堵转）**：旧写法 PWM 固定 IN1、方向只切 IN2，反转时两个输入都为高 = 刹车。修复：PWM 按方向切换到对应 IN 脚（前进 FWD 脚 PWM、后退 REV 脚 PWM），4 个 LEDC 通道。
3. **电机 LEDC 通道避开摄像头 XCLK（通道 0）**：电机用通道 4/5/6/7。
4. **App 摇杆"拖动保持时车停"**：App 只在摇杆值变化时发送，用户拖到某位置停住 → 固件 300ms 看门狗停车。修复：非中位时持续发送（25Hz）。
5. **App 摇杆松手回中**：改用 Listener 指针级监听，松手必回中。
6. **固件崩溃（松手不停转/失联）**：诊断用 UDP 日志在 loop 高频发送（每 40ms）导致 WiFi 栈崩溃，看门狗失效、电机保持最后状态。修复：移除 UDP 高频日志，改回纯串口日志。压测（满幅转向 10s + 快速切换 20 次）通过。
7. **测试工具教训**：send_cmd 只发一次指令会被固件 300ms 看门狗停车 → 用 send_hold（持续发送）模拟 App；读串口会复位芯片踢断 TCP → 用 logcat（App 侧）+ 插底座读串口（固件侧）分开诊断。
8. **电机低油门不启动**：7.4V + L298N 压降下，<40% PWM 电机不转（正常物理现象），满油门 60% 正常。用户操控时推到中高油门即可。

| 优雅断开检测 | ⚠️ 见下 |

### 发现并修复：断开检测失效
- **现象**：主动 close 后 8s 内收不到 [tcp] disconnected，断开检测不触发
- **根因 1**：ESP32 Arduino `WiFiClient::connected()` 用 `recv(fd,&dummy,0,MSG_DONTWAIT)` 探测，优雅关闭（FIN→CLOSE_WAIT）时 recv(0) 返回 0 不报错，走 default 分支 → connected() 永远 true
- **修复**：新增 `ctrlConnected()`，用 `recv(fd,&b,1,MSG_PEEK|MSG_DONTWAIT)` 探测 EOF（返回 0 = 对端关闭；EWOULDBLOCK = 无数据但连接正常）
- **根因 2（本质）**：实测探测返回 `res=-1 errno=11(EWOULDBLOCK)` → **FIN 包在 Wi-Fi 链路丢失**，连接为半开（half-open）。任何探测都检测不到"FIN 没到达"的连接
- **结论**：安全由**看门狗兜底**（指令停止到达即 300ms 停车，覆盖所有断开形式）；断开检测仅诊断用途。半开连接下 ESP32 仍 ACK 缓冲 app 指令，因此**只要 app 松手发停止帧，车就能停**；重连时状态机重置杜绝旧信号回放
- 不引入心跳/回执（用户决定：为视频流让带宽）
